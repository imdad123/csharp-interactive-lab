GITHUB ENGINEERING

GitHub repositories, collaboration and governance

A practical reference for professional source control, pull requests, security and release management.

Repository strategy

Use one repository per independently versioned product/service unless a monorepo is justified. Keep application code, tests, infrastructure and documentation organized. Add README, license where appropriate, CODEOWNERS, contribution guidance and security policy.

Branch and pull request workflow

main
  ├── feature/patient-registration
  ├── fix/appointment-double-booking
  └── chore/update-dotnet-sdk

Protect the default branch. Require pull requests, successful checks and review. Use short-lived branches and small changes. Prefer squash or rebase merge according to team policy; avoid force-pushing shared branches.

Useful GitHub repository files

  • README.md — purpose, prerequisites, setup, run, test and deployment.
  • .gitignore — generated files, secrets, IDE output and local configuration.
  • .editorconfig — consistent formatting conventions.
  • CODEOWNERS — assign reviewers to sensitive areas.
  • .github/pull_request_template.md — problem, solution, tests, risks and screenshots.
  • .github/ISSUE_TEMPLATE/ — bug reports and feature requests.
  • .github/workflows/ — CI and deployment workflow definitions.

Pull request quality checklist

  • Does the change solve one clearly described problem?
  • Are business rules tested, including boundary and failure cases?
  • Are SQL changes parameterized and migration-safe?
  • Are authorization, privacy and audit requirements addressed?
  • Are logs useful without exposing patient data or secrets?
  • Are configuration and deployment changes documented?
  • Can the change be rolled back safely?

GitHub security and governance

Enable secret scanning and push protection where available, dependency alerts and updates, code scanning, branch protection/rulesets and least-privilege permissions. Never store API keys, passwords, database connection strings or private certificates in source control. Rotate any secret that was committed.

Release and versioning

Use tags and releases, semantic versioning where it fits, changelogs, immutable build artifacts and deployment approvals. Distinguish source commit, build artifact and deployed release so production can be traced back to an exact commit.
