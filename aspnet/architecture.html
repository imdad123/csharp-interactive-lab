Architecture, microservices and distributed systems

The roadmap includes microservices, message brokers, API gateways, containerization, cloud, .NET Aspire, Dapr, Orleans and supporting libraries. Learn the distributed-system problems before choosing tools.

1. Modular monolith before microservices

A modular monolith deploys as one application but separates domain capabilities into modules with explicit boundaries. It is often simpler to operate than microservices while still allowing clear ownership and future extraction.

src/
  Hospital.Api/
  Modules/
    Patients/
      Patients.Domain/
      Patients.Application/
      Patients.Infrastructure/
    Appointments/
      Appointments.Domain/
      Appointments.Application/
      Appointments.Infrastructure/
  BuildingBlocks/
tests/

Do not split into microservices only to create more projects. Split when independent deployment, scaling, ownership or fault isolation outweighs network, data consistency and operational complexity.

2. Message broker fundamentals

Message brokers decouple producers and consumers. RabbitMQ is commonly used for work queues and routing; Kafka is a distributed event log/streaming platform; Azure Service Bus provides managed enterprise messaging. ActiveMQ and NetMQ address other messaging scenarios. Evaluate delivery guarantees, ordering, retention, throughput and operations.

public sealed record InvoiceFinalized(
    Guid EventId,
    int InvoiceId,
    int PatientId,
    DateTime OccurredAtUtc);

// Producer intent after the invoice transaction commits:
await messageBus.PublishAsync(
    new InvoiceFinalized(Guid.NewGuid(), invoice.Id,
        invoice.PatientId, DateTime.UtcNow),
    cancellationToken);

The exact API depends on the chosen broker/library. This event contract is illustrative; durable publishing should use an outbox when a database commit and message publication must stay consistent.

3. Consumer idempotency

public async Task HandleAsync(InvoiceFinalized message, CancellationToken ct)
{
    if (await processedMessages.ExistsAsync(message.EventId, ct))
        return;

    await receiptWorkflow.SendAsync(message.InvoiceId, ct);
    await processedMessages.MarkProcessedAsync(message.EventId, ct);
}

In a production consumer, processing and recording the idempotency key should be atomic where possible. The simplified example shows the concept but can race if two deliveries run concurrently.

4. Message bus libraries

MassTransit, NServiceBus and EasyNetQ provide higher-level message abstractions and patterns over supported transports. They can reduce boilerplate but add framework concepts and operational conventions. Choose one based on transport support, outbox/saga features, licensing, team experience and ecosystem fit.

5. Resilience and Polly

Network calls fail transiently. Resilience policies can include timeouts, retries, circuit breakers and concurrency limits. Retries must be bounded and safe for the operation.

// Example using the Microsoft.Extensions.Http.Resilience integration package.
builder.Services.AddHttpClient<BillingGatewayClient>()
    .AddStandardResilienceHandler();

Use resilience handlers for remote dependencies, but do not retry validation errors or non-idempotent payment operations without an idempotency design.

6. Validation and mediator libraries

FluentValidation offers expressive request validators. MediatR provides request/handler and notification patterns. These libraries can help organize application workflows, but neither is required by ASP.NET Core; direct service calls are often simpler for small systems.

public sealed class RegisterPatientValidator
    : AbstractValidator<RegisterPatientRequest>
{
    public RegisterPatientValidator()
    {
        RuleFor(x => x.FullName).NotEmpty().MaximumLength(150);
        RuleFor(x => x.Mrn).NotEmpty().MaximumLength(30);
    }
}

Register validators with DI using the integration appropriate to the installed FluentValidation version. Keep domain invariants enforced in the domain/application layer, not only in HTTP request validators.

7. Containers and orchestration

docker build -t hospital-api:local .
docker run --rm -p 8080:8080   -e ASPNETCORE_URLS=http://+:8080   hospital-api:local

Docker packages the application and runtime dependencies into an image. Kubernetes orchestrates containerized workloads across a cluster and adds deployment, service discovery, scaling and health management. Do not introduce Kubernetes if a simpler managed container service meets the requirement.

8. .NET Aspire, Dapr and Orleans

  • .NET Aspire: developer tooling and orchestration for distributed .NET applications, including local composition, service discovery and observability integrations.
  • Dapr: building blocks for service invocation, pub/sub, state and secrets through sidecars and APIs.
  • Orleans: virtual actor model for stateful distributed applications.
  • Steeltoe: integrations for cloud-native patterns in supported environments.

These are specialized platform choices. Evaluate runtime model, operational footprint, deployment environment and long-term support before adopting them.

9. Distributed locks and consistency

A distributed lock coordinates work across multiple application instances, but lease expiry, process pauses and network partitions can make naive locks unsafe. Prefer database uniqueness constraints, optimistic concurrency, idempotency and partitioned work where those solve the problem. Use a distributed lock only when the shared critical section truly requires one.

10. Benchmarking and performance

Use BenchmarkDotNet for repeatable microbenchmarks and production telemetry/profilers for system-level bottlenecks. Benchmark realistic data and include allocations, throughput and latency distributions. Do not optimize a method based only on intuition.

[MemoryDiagnoser]
public class PatientSearchBenchmarks
{
    private readonly List<string> _names =
        Enumerable.Range(1, 10_000).Select(i => $"Patient {i}").ToList();

    [Benchmark]
    public bool AnyMatch()
        => _names.Any(name => name == "Patient 9999");

    [Benchmark]
    public string? FirstMatch()
        => _names.FirstOrDefault(name => name == "Patient 9999");
}

Practice

  1. Separate Patients and Appointments into modules in one deployable application.
  2. Design an InvoiceFinalized event and an idempotent consumer.
  3. Explain when RabbitMQ, Kafka or Azure Service Bus fits your workload.
  4. Containerize the API and add a health check.
  5. Document the operational reason before choosing microservices, Dapr, Orleans or Kubernetes.
