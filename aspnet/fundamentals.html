ASP.NET Core hosting and fundamentals

ASP.NET Core is a cross-platform framework for HTTP APIs and web applications. It runs on .NET and processes requests through a configurable pipeline.

1. Create and run an application

dotnet new webapi -n Hospital.Api
cd Hospital.Api
dotnet run

The .NET SDK creates the project and restores packages. The application is compiled and hosted by the .NET runtime.

2. Understand Program.cs

var builder = WebApplication.CreateBuilder(args);

// Register framework and application services.
builder.Services.AddEndpointsApiExplorer();
builder.Services.AddSwaggerGen();

var app = builder.Build();

// Configure the HTTP request pipeline.
if (app.Environment.IsDevelopment())
{
    app.UseSwagger();
    app.UseSwaggerUI();
}

app.MapGet("/", () => Results.Ok(new
{
    service = "Hospital API",
    status = "running"
}));

app.Run();

WebApplication.CreateBuilder prepares configuration, logging, dependency injection and hosting defaults. Services are registered before Build. Middleware and endpoints are configured after the application is built and before Run.

3. Kestrel and hosting

Kestrel is the cross-platform HTTP server commonly used by ASP.NET Core. In production it may run directly or behind a reverse proxy/load balancer. The proxy can terminate TLS, forward requests and distribute traffic; configure forwarded headers correctly when deployed behind one.

// Example configuration in appsettings.json
{
  "Urls": "http://localhost:5080"
}
// Or configure an address from the command line:
dotnet run --urls http://localhost:5080

Do not hard-code production endpoints into source code. Use environment-specific configuration and deployment settings.

4. Environments

if (app.Environment.IsDevelopment())
{
    app.UseDeveloperExceptionPage();
}
else
{
    app.UseExceptionHandler("/error");
    app.UseHsts();
}

Common environments are Development, Staging and Production. Environment names control configuration and environment-specific behavior; they are not a security boundary by themselves.

5. Routing and endpoint mapping

app.MapGet("/api/doctors", () =>
    Results.Ok(new[] { "Dr. Ali", "Dr. Sara" }));

app.MapGet("/api/doctors/{id:int}", (int id) =>
{
    if (id == 1)
        return Results.Ok(new { Id = id, Name = "Dr. Ali" });

    return Results.NotFound();
})
.WithName("GetDoctorById");

Route templates can include parameters and constraints. Avoid duplicate route definitions with the same HTTP method and matching template.

6. Request lifecycle mental model

  1. The server accepts an HTTP request.
  2. The request enters the middleware pipeline.
  3. Routing selects an endpoint.
  4. Authentication and authorization middleware establish and enforce identity rules.
  5. Endpoint code invokes application services.
  6. The application returns a result which is serialized into an HTTP response.

7. Organize a solution

Hospital.sln
src/
  Hospital.Api/
  Hospital.Application/
  Hospital.Domain/
  Hospital.Infrastructure/
tests/
  Hospital.UnitTests/
  Hospital.IntegrationTests/

Start smaller when the domain is small. Split projects when boundaries provide real value; avoid creating empty layers and pass-through abstractions without a reason.

Common mistakes

  • Registering services after builder.Build().
  • Putting database queries and business rules directly in endpoint lambdas as the API grows.
  • Exposing detailed exception pages in production.
  • Assuming localhost binding is reachable from another machine or container.
  • Ignoring proxy and forwarded-header configuration in hosted environments.

Practice

  1. Create Hospital.Api and run it locally.
  2. Add /health and /api/departments endpoints.
  3. Run the app under Development and Production environment names.
  4. Move department data into a service registered through DI.
