TOPIC GUIDE

Real-time communication and background processing

1. SignalR for live updates

SignalR lets the server push events to connected clients. In a hospital dashboard it can notify staff when bed occupancy or an appointment queue changes. Do not use SignalR as the durable source of truth; persist the change first, then publish a notification.

public sealed class HospitalHub : Hub
{
    public Task JoinWard(string wardCode)
        => Groups.AddToGroupAsync(Context.ConnectionId, $"ward:{wardCode}");
}

// Program.cs
builder.Services.AddSignalR();
app.MapHub<HospitalHub>("/hubs/hospital");

// From an application service after a successful database commit:
public sealed class WardNotifier(IHubContext<HospitalHub> hub)
{
    public Task NotifyBedChanged(string wardCode, int bedId, bool occupied)
        => hub.Clients.Group($"ward:{wardCode}")
            .SendAsync("BedChanged", new { bedId, occupied });
}

2. WebSockets

WebSockets provide a persistent bidirectional connection. SignalR can use WebSockets and negotiate other transports where configured. Prefer SignalR for typical application messaging; use raw WebSockets when you specifically need a lower-level protocol and are prepared to own connection management.

3. BackgroundService

Use hosted services for work that belongs to the application process and is safe to run there, such as periodic cleanup or polling. Long-running or business-critical work may need a durable queue and separate worker process.

public sealed class AppointmentReminderWorker(
    IServiceScopeFactory scopeFactory,
    ILogger<AppointmentReminderWorker> logger)
    : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        using var timer = new PeriodicTimer(TimeSpan.FromMinutes(1));

        while (await timer.WaitForNextTickAsync(stoppingToken))
        {
            await using var scope = scopeFactory.CreateAsyncScope();
            var sender = scope.ServiceProvider
                .GetRequiredService<IAppointmentReminderSender>();

            await sender.SendDueRemindersAsync(stoppingToken);
            logger.LogInformation("Appointment reminder cycle finished");
        }
    }
}

Register with builder.Services.AddHostedService<AppointmentReminderWorker>(). Create a DI scope for scoped dependencies such as DbContext. Handle cancellation and make processing idempotent so a retry does not send duplicate reminders.

4. Scheduling libraries

Hangfire, Quartz.NET and Coravel provide scheduling abstractions and persistence/integration options. Choose based on durability, clustering, dashboard/security requirements and operational complexity. A simple BackgroundService is enough for many periodic tasks; do not introduce a scheduler without a requirement.

5. Message brokers and message bus

RabbitMQ, Kafka and Azure Service Bus solve different messaging problems. MassTransit, NServiceBus and EasyNetQ add higher-level patterns on top of transports. A broker decouples producers and consumers, buffers work and supports independent scaling, but adds infrastructure and delivery semantics that must be handled.

6. Reliability patterns

  • Idempotency: process the same message more than once without duplicating the business effect.
  • Retries: retry transient failures with bounded backoff; avoid retrying permanent validation errors.
  • Dead-letter queue: isolate messages that repeatedly fail for investigation.
  • Outbox: commit business data and an outgoing event record in one database transaction, then publish it asynchronously.
  • Ordering: define whether ordering is required per patient, appointment or aggregate.

Practice

  1. Build a SignalR hub that broadcasts a bed occupancy change.
  2. Create a hosted service that scans appointments needing reminders.
  3. Use a scoped service inside the worker via IServiceScopeFactory.
  4. Design an idempotency key for appointment reminder events.
  5. Draw an outbox workflow before adding a message broker.
