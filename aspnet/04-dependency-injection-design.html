GUIDE 04 · ASP.NET CORE / .NET 10

Dependency injection, configuration and application design

Build maintainable services with explicit dependencies and clear boundaries. Each topic includes its purpose, the knowledge to acquire, a practical example and an implementation exercise.

Learning rule: Do not just read the code. Create the project, run it, test normal and failure cases, inspect logs and SQL, then explain the trade-offs in your own words. Examples are focused teaching snippets; add the required namespaces, packages and surrounding application types when integrating them.

TOPIC 01

Dependency injection fundamentals

Why this matters

DI separates object creation from business behavior. It makes dependencies visible, replaceable and testable rather than constructing infrastructure inside every class.

What you must learn

Learn the built-in container, constructor injection, registrations, composition root, interface boundaries and avoiding service locator patterns.

Practical code example

builder.Services.AddScoped<IAppointmentService, AppointmentService>();
builder.Services.AddScoped<IAppointmentRepository, SqlAppointmentRepository>();

public sealed class AppointmentService(IAppointmentRepository repository)
    : IAppointmentService
{
    public Task<Appointment?> GetAsync(Guid id, CancellationToken ct) =>
        repository.GetAsync(id, ct);
}

Build / practise

Move database access behind an interface and test the application service without starting SQL Server.

TOPIC 02

Service lifetimes: transient, scoped, singleton

Why this matters

A wrong lifetime can cause shared mutable state, disposed-object errors or data leakage between requests. EF Core DbContext is normally scoped.

What you must learn

Learn transient/scoped/singleton semantics, scope boundaries, captive dependencies, `IServiceScopeFactory` and background-service scopes.

Practical code example

builder.Services.AddTransient<IEmailFormatter, EmailFormatter>();
builder.Services.AddScoped<IAppointmentService, AppointmentService>();
builder.Services.AddDbContext<HospitalDbContext>(options =>
    options.UseSqlServer(connectionString));

Build / practise

Identify why injecting a scoped DbContext into a singleton is unsafe and implement a background worker that creates a scope per job.

TOPIC 03

Options pattern and strongly typed settings

Why this matters

Reading arbitrary configuration strings throughout the codebase spreads key names and makes invalid configuration fail late.

What you must learn

Learn `IOptions`, `IOptionsSnapshot`, `IOptionsMonitor`, binding, validation and reload behavior.

Practical code example

builder.Services.AddOptions<SmsOptions>()
    .BindConfiguration("Sms")
    .Validate(x => Uri.TryCreate(x.BaseUrl, UriKind.Absolute, out _), "Sms BaseUrl is invalid")
    .ValidateOnStart();

public sealed class SmsOptions { public string BaseUrl { get; init; } = ""; }

Build / practise

Move SMS and payment gateway settings into validated options. Keep credentials in secret storage, not committed JSON.

TOPIC 04

Layered architecture and dependency direction

Why this matters

A maintainable system separates domain rules from delivery and infrastructure. The domain should not depend on ASP.NET Core or EF Core.

What you must learn

Learn presentation, application, domain and infrastructure responsibilities; dependency direction; DTO mapping; ports and adapters; avoiding anemic service layers.

Practical code example

// Domain project: no ASP.NET Core or EF Core dependency
public sealed class Appointment
{
    public Guid Id { get; private set; }
    public DateTimeOffset StartsAt { get; private set; }
    public void Reschedule(DateTimeOffset startsAt)
    {
        if (startsAt <= DateTimeOffset.UtcNow) throw new InvalidOperationException("Start time must be in the future.");
        StartsAt = startsAt;
    }
}

Build / practise

Split the solution into API, Application, Domain and Infrastructure. Make the Domain project compile without web or database packages.

TOPIC 05

Clean Architecture, modular monolith and vertical slices

Why this matters

Clean Architecture is a way to protect business rules from infrastructure details. A modular monolith gives strong module boundaries without the operational cost of microservices.

What you must learn

Learn use-case boundaries, vertical slices, feature folders, module ownership, dependency rules, MediatR trade-offs and when not to add abstractions.

Practical code example

public sealed record BookAppointmentCommand(Guid PatientId, Guid DoctorId, DateTimeOffset StartsAt);
public sealed class BookAppointmentHandler(IAppointmentRepository appointments)
{
    public async Task<Guid> Handle(BookAppointmentCommand command, CancellationToken ct)
    {
        var appointment = Appointment.Book(command.PatientId, command.DoctorId, command.StartsAt);
        await appointments.AddAsync(appointment, ct);
        return appointment.Id;
    }
}

Build / practise

Build booking as a vertical slice: endpoint, request, validation, handler, domain operation, persistence and tests. Avoid premature microservices.
