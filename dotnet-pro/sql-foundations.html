MODULE 01 · PROFESSIONAL GUIDE

T-SQL foundations and relational thinking

Tables, keys, constraints, joins, grouping, subqueries, CTEs, window functions, views and normalization.

Why this module matters: production systems fail when engineers know syntax but not data integrity, operational behavior, security boundaries or failure modes. Learn the reasoning, then implement each exercise in the HMS solution.

1. Relational modeling and normalization

Why it exists. A database must represent facts without update anomalies. Normalization separates independent entities and relationships.

Professional practice. Model patient identity separately from appointments, visits and invoices; use foreign keys and constraints to protect invariants.

Example / implementation direction

CREATE TABLE dbo.Patient (PatientId bigint IDENTITY PRIMARY KEY, MedicalRecordNo varchar(20) NOT NULL UNIQUE, FullName nvarchar(160) NOT NULL, DateOfBirth date NULL);

HMS exercise: Design Patient, Doctor, Appointment and Department tables with keys and appropriate nullability.

2. Keys, constraints and data integrity

Why it exists. Application validation cannot protect data from scripts, imports or concurrent requests. Database constraints are the final integrity boundary.

Professional practice. Use primary/foreign keys, UNIQUE, CHECK and NOT NULL constraints; choose delete behavior deliberately.

Example / implementation direction

ALTER TABLE dbo.Appointment ADD CONSTRAINT CK_Appointment_EndAfterStart CHECK (EndAt > StartAt);

HMS exercise: Prevent duplicate appointment slots and invalid date ranges at database level.

3. Joins and set-based querying

Why it exists. Relational systems operate on sets; row-by-row application loops create extra round trips and inconsistent results.

Professional practice. Understand INNER, LEFT, CROSS joins, cardinality and duplicate multiplication.

Example / implementation direction

SELECT a.AppointmentId, p.FullName FROM dbo.Appointment AS a JOIN dbo.Patient AS p ON p.PatientId=a.PatientId;

HMS exercise: List appointments with patient and doctor details in one query.

4. Grouping and aggregate queries

Why it exists. Reports need correct aggregation at the intended grain; joining multiple one-to-many tables can multiply totals.

Professional practice. Use GROUP BY, HAVING, conditional aggregation and pre-aggregate child sets before joining.

Example / implementation direction

SELECT CAST(StartAt AS date) AS VisitDate, COUNT_BIG(*) AS AppointmentCount FROM dbo.Appointment GROUP BY CAST(StartAt AS date);

HMS exercise: Create daily appointment and collection summaries with correct totals.

5. CTEs, subqueries and window functions

Why it exists. Complex reports become clearer when intermediate sets are named and analytic calculations are separated from row filtering.

Professional practice. Use CTEs for readable query stages; use ROW_NUMBER, LAG, SUM OVER and PARTITION BY for analytics.

Example / implementation direction

WITH Ranked AS (SELECT PatientId, StartAt, ROW_NUMBER() OVER(PARTITION BY PatientId ORDER BY StartAt DESC) AS rn FROM dbo.Appointment) SELECT PatientId, StartAt FROM Ranked WHERE rn=1;

HMS exercise: Find each patient's latest appointment without a cursor.

6. Views and stored query contracts

Why it exists. A view can centralize reusable relational logic, but it is not automatically a performance optimization or security boundary.

Professional practice. Keep views focused, document dependencies and parameterize application queries rather than concatenating SQL.

Example / implementation direction

CREATE VIEW dbo.vw_AppointmentSummary AS SELECT AppointmentId, PatientId, DoctorId, StartAt, Status FROM dbo.Appointment;

HMS exercise: Create a read view for an appointment dashboard and document its grain.

7. Transactions and isolation

Why it exists. Multi-step business changes must commit or roll back as one unit, while isolation controls what concurrent work can observe.

Professional practice. Understand ACID, isolation levels, deadlocks, lock duration and retry safety.

Example / implementation direction

SET XACT_ABORT ON; BEGIN TRY BEGIN TRAN; UPDATE dbo.Bed SET IsOccupied=1 WHERE BedId=@BedId AND IsOccupied=0; IF @@ROWCOUNT=0 THROW 50001,'Bed unavailable',1; INSERT dbo.Admission(BedId,PatientId) VALUES(@BedId,@PatientId); COMMIT; END TRY BEGIN CATCH IF XACT_STATE()<>0 ROLLBACK; THROW; END CATCH;

HMS exercise: Implement atomic bed allocation and admission creation.

8. Query plans and index fundamentals

Why it exists. A query can be logically correct and still be too slow. The optimizer chooses access paths based on estimates, indexes and statistics.

Professional practice. Read actual execution plans; distinguish scans, seeks, lookups, joins, spills and bad cardinality estimates.

Example / implementation direction

CREATE INDEX IX_Appointment_Doctor_StartAt ON dbo.Appointment(DoctorId, StartAt) INCLUDE (PatientId, Status);

HMS exercise: Measure a doctor schedule query before and after a workload-justified index.

  • Have you tested success, invalid input, concurrency and failure paths?
