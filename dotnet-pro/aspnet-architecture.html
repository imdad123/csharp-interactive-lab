MODULE 05 · PROFESSIONAL GUIDE

ASP.NET Core application architecture

Hosting, Kestrel, middleware, endpoint routing, controllers, Minimal APIs, DI lifetimes, modular monolith, vertical slices and clean boundaries.

Why this module matters: production systems fail when engineers know syntax but not data integrity, operational behavior, security boundaries or failure modes. Learn the reasoning, then implement each exercise in the HMS solution.

1. Hosting model and request pipeline

Why it exists. ASP.NET Core composes hosting, middleware and endpoints; ordering determines which requests are authenticated, transformed or rejected.

Professional practice. Understand WebApplication, Kestrel, reverse proxies and middleware short-circuiting; place exception handling and security middleware deliberately.

Example / implementation direction

var app = builder.Build();
app.UseExceptionHandler();
app.UseHttpsRedirection();
app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();

HMS exercise: Trace a request through middleware and explain ordering.

2. Controllers versus Minimal APIs

Why it exists. Both are first-class endpoint models; choose based on team conventions, complexity and consistency rather than ideology.

Professional practice. Use controllers for convention-rich larger APIs or Minimal APIs for focused endpoint groups; keep business rules outside endpoint handlers.

Example / implementation direction

var group = app.MapGroup("/api/appointments").RequireAuthorization();
group.MapGet("/{id:int}", GetAppointment);

HMS exercise: Implement the same read endpoint using both styles and compare testability.

3. Application boundaries and vertical slices

Why it exists. Large service classes and generic repositories often hide use cases; vertical slices keep behavior, validation and tests close together.

Professional practice. Organize around business capabilities and explicit commands/queries; use abstractions only when they protect a real boundary.

Example / implementation direction

public sealed record BookAppointmentCommand(long PatientId,int DoctorId,DateTime StartAt);

HMS exercise: Implement BookAppointment as a use case with explicit dependencies.

4. Domain modeling and invariants

Why it exists. Business rules should not depend on HTTP controllers or database persistence details.

Professional practice. Model meaningful entities and value objects; enforce invariants in domain operations and avoid anemic data bags for complex behavior.

Example / implementation direction

public sealed class Appointment { public void Confirm(){ if(Status!=AppointmentStatus.Pending) throw new InvalidOperationException("Only pending appointments can be confirmed."); Status=AppointmentStatus.Confirmed; } }

HMS exercise: Define allowed appointment state transitions and test invalid transitions.

5. Background services and request cancellation

Why it exists. Requests can be aborted and background work can outlive the request; confusing the two causes lost or orphaned work.

Professional practice. Pass CancellationToken through I/O; use hosted services or durable queues for work that must survive process restarts.

Example / implementation direction

app.MapGet("/api/patients/{id}", async (long id, HospitalDbContext db, CancellationToken ct) => await db.Patients.FindAsync([id], ct));

HMS exercise: Propagate cancellation through a report endpoint and move durable work to a queue.

6. Architecture decisions and modular monolith

Why it exists. A modular monolith offers clear module boundaries without distributed deployment complexity.

Professional practice. Separate modules by business capability, own their data access, publish internal events carefully and record decisions with ADRs.

Example / implementation direction

// Modules: Patients, Scheduling, Admissions, Pharmacy, Billing
// Each module owns its application services and persistence boundary.

HMS exercise: Draw HMS module dependencies and prevent direct cross-module table ownership.

Module review checklist

  • Can you explain the problem this tool or pattern solves?
  • Can you implement it without copying a template blindly?
  • Have you tested success, invalid input, concurrency and failure paths?
  • Can you explain its security, performance and operational trade-offs?
