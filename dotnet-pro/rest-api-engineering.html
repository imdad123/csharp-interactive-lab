MODULE 07 · PROFESSIONAL GUIDE

Professional REST API engineering

Resource design, HTTP semantics, pagination, filtering, sorting, versioning, OpenAPI, idempotency, ETags, file handling and background jobs.

Why this module matters: production systems fail when engineers know syntax but not data integrity, operational behavior, security boundaries or failure modes. Learn the reasoning, then implement each exercise in the HMS solution.

1. Resource-oriented REST design

Why it exists. REST endpoints should model resources and state transitions rather than expose database tables or RPC names indiscriminately.

Professional practice. Use nouns, consistent nesting, correct HTTP verbs and explicit action endpoints only for domain commands that do not map cleanly to CRUD.

Example / implementation direction

GET /api/patients/42
POST /api/appointments
POST /api/appointments/900/confirm

HMS exercise: Design patient, appointment and admission endpoint contracts.

2. HTTP semantics and status codes

Why it exists. Correct status codes allow browsers, proxies and clients to reason about outcomes.

Professional practice. Distinguish 200, 201 with Location, 202, 204, 400, 401, 403, 404, 409, 422, 429 and 5xx.

Example / implementation direction

return Results.Created($"/api/patients/{patient.Id}", PatientDto.From(patient));

HMS exercise: Specify status codes for successful creation, conflicts and asynchronous report generation.

3. Pagination, filtering and sorting

Why it exists. Unbounded collection endpoints create memory, latency and denial-of-service risks.

Professional practice. Set maximum page sizes, stable ordering and allowlisted sort fields; use keyset pagination for deep sequential navigation.

Example / implementation direction

var page = await query.OrderBy(x => x.Id).Where(x => x.Id > cursor).Take(Math.Clamp(size,1,100)).ToListAsync(ct);

HMS exercise: Build a cursor-paginated patient history endpoint.

4. OpenAPI and API documentation

Why it exists. An API contract helps frontend, mobile and integration teams work independently.

Professional practice. Describe schemas, auth, response codes, examples and deprecation; generate and review OpenAPI as a build artifact.

Example / implementation direction

builder.Services.AddOpenApi();
if (app.Environment.IsDevelopment()) app.MapOpenApi();

HMS exercise: Publish an OpenAPI contract and use it to coordinate Angular and MAUI clients.

5. Versioning and compatibility

Why it exists. Clients deploy independently; breaking response or behavior changes can disrupt older mobile apps.

Professional practice. Prefer additive changes, explicit deprecation and version only when compatibility cannot be preserved.

Example / implementation direction

// Example route convention: /api/v1/patients
// Maintain compatibility while clients migrate to v2.

HMS exercise: Plan a patient DTO change while supporting an older mobile app.

6. Idempotency, concurrency and file endpoints

Why it exists. Retries are normal in distributed networks; duplicate commands and stale writes must be handled explicitly.

Professional practice. Use idempotency keys for retried creates/payments, ETags or rowversion for optimistic concurrency, and strict file limits/scanning.

Example / implementation direction

// Require If-Match for updates; return 412 when the supplied ETag is stale.

HMS exercise: Prevent duplicate payment submission and stale admission updates.

Module review checklist

  • Can you explain the problem this tool or pattern solves?
  • Can you implement it without copying a template blindly?
  • Have you tested success, invalid input, concurrency and failure paths?
  • Can you explain its security, performance and operational trade-offs?
