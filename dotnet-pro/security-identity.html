MODULE 08 · PROFESSIONAL GUIDE

Authentication and application security

ASP.NET Core Identity, JWT, OAuth 2.0, OpenID Connect, cookies, policies, claims, resource authorization, CORS, CSRF, rate limits and OWASP API risks.

Why this module matters: production systems fail when engineers know syntax but not data integrity, operational behavior, security boundaries or failure modes. Learn the reasoning, then implement each exercise in the HMS solution.

1. Authentication versus authorization

Why it exists. Authentication establishes identity; authorization decides whether that identity may perform an operation on a resource.

Professional practice. Use established identity standards and policy-based authorization; never rely on hidden UI controls.

Example / implementation direction

builder.Services.AddAuthorizationBuilder().AddPolicy("Appointments.Read", p => p.RequireClaim("permission","appointments.read"));

HMS exercise: Protect schedule reads separately from appointment creation.

2. JWT, OAuth 2.0 and OpenID Connect

Why it exists. Tokens enable delegated and federated access but are not a replacement for secure identity lifecycle management.

Professional practice. Use a trusted identity provider, validate issuer/audience/signature/expiry and avoid hand-rolled token formats.

Example / implementation direction

builder.Services.AddAuthentication().AddJwtBearer(options => { options.Authority = config["Identity:Authority"]; options.Audience = "hospital-api"; });

HMS exercise: Configure API token validation against a development identity provider.

3. ASP.NET Core Identity and account lifecycle

Why it exists. Identity provides password hashing, lockout, confirmation and token workflows that are easy to get wrong when custom-built.

Professional practice. Use supported Identity flows, MFA where appropriate, secure reset, session revocation strategy and audit events.

Example / implementation direction

builder.Services.AddIdentityCore().AddRoles().AddEntityFrameworkStores();

HMS exercise: Implement staff account lifecycle and role assignment.

4. Resource-level authorization and IDOR

Why it exists. A valid user can still be unauthorized to access a particular patient's record; checking only roles is insufficient.

Professional practice. Authorize against the requested resource and organizational scope on every read and write.

Example / implementation direction

var result = await authorization.AuthorizeAsync(user, patient, "PatientAccess");

HMS exercise: Ensure a ward user cannot retrieve records outside permitted scope.

5. Browser security, CORS and CSRF

Why it exists. Browser credentials and cross-origin rules create risks distinct from bearer-token API calls.

Professional practice. Allow exact trusted origins; understand cookie SameSite/anti-forgery protections and avoid wildcard credentialed CORS.

Example / implementation direction

policy.WithOrigins("https://portal.example.com").AllowAnyHeader().AllowAnyMethod();

HMS exercise: Configure development and production Angular origins safely.

6. API threat controls and sensitive data

Why it exists. APIs are exposed to broken object authorization, excessive data exposure, resource exhaustion and injection.

Professional practice. Apply least privilege, rate limits, payload limits, secret management, audit logging and privacy-aware telemetry.

Example / implementation direction

builder.Services.AddRateLimiter(o => o.AddFixedWindowLimiter("api", x => { x.PermitLimit=100; x.Window=TimeSpan.FromMinutes(1); }));

HMS exercise: Threat-model patient search, report export and login endpoints.
