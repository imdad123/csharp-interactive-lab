MODULE 03 · PROFESSIONAL GUIDE

EF Core and data access

DbContext, entities, relationships, migrations, LINQ translation, tracking, projections, transactions, concurrency and raw SQL.

Why this module matters: production systems fail when engineers know syntax but not data integrity, operational behavior, security boundaries or failure modes. Learn the reasoning, then implement each exercise in the HMS solution.

1. DbContext and unit-of-work lifetime

Why it exists. DbContext tracks changes and coordinates a unit of work; sharing it across concurrent requests causes unsafe state and race conditions.

Professional practice. Use a scoped context per web request or IDbContextFactory for deliberate background/parallel workflows; never run parallel operations on one context.

Example / implementation direction

builder.Services.AddDbContext(o => o.UseSqlServer(builder.Configuration.GetConnectionString("HospitalDb")));

HMS exercise: Register the context and explain why a singleton DbContext is unsafe.

2. Entity mapping and relationships

Why it exists. EF Core maps an object model to relational constraints; conventions are helpful but production schema intent should be explicit.

Professional practice. Configure keys, lengths, precision, indexes, required relationships, delete behavior and owned/value objects with Fluent API.

Example / implementation direction

modelBuilder.Entity().Property(x => x.TotalAmount).HasPrecision(18,2);
modelBuilder.Entity().HasIndex(x => x.MedicalRecordNo).IsUnique();

HMS exercise: Map patient, appointment and invoice entities with explicit database constraints.

3. Migrations and schema governance

Why it exists. Migrations record schema evolution, but generated changes need review and controlled deployment.

Professional practice. Generate idempotent scripts or migration bundles; inspect destructive operations and coordinate schema compatibility with deployed app versions.

Example / implementation direction

dotnet ef migrations add AddAppointmentStatus
dotnet ef migrations script --idempotent -o artifacts/migration.sql

HMS exercise: Generate and review a migration; do not auto-apply risky schema changes at app startup.

4. LINQ translation and efficient queries

Why it exists. LINQ expressions are translated to SQL; a query that looks simple in C# may cause N+1 calls, client evaluation or large result sets.

Professional practice. Project to DTOs, use AsNoTracking for read paths, paginate, inspect SQL and understand split versus single queries.

Example / implementation direction

var rows = await db.Appointments.AsNoTracking().Where(x => x.StartAt >= from).OrderBy(x => x.StartAt).Select(x => new AppointmentListItem(x.Id,x.Patient.FullName,x.StartAt)).ToListAsync(ct);

HMS exercise: Build a paged doctor schedule and inspect its generated SQL.

5. Tracking, updates and concurrency

Why it exists. Change tracking is convenient for aggregate updates but unnecessary tracking wastes memory on read-heavy endpoints.

Professional practice. Use tracked entities for updates, projections for reads, concurrency tokens for contested data and handle DbUpdateConcurrencyException.

Example / implementation direction

modelBuilder.Entity().Property(x => x.RowVersion).IsRowVersion();

HMS exercise: Prevent two staff members from assigning the same bed using a rowversion token.

6. Transactions and raw SQL boundaries

Why it exists. EF Core manages transactions for SaveChanges, but multi-step workflows and mixed SQL operations need explicit boundaries.

Professional practice. Use Database.BeginTransactionAsync when multiple operations must be atomic; parameterize FromSql and ExecuteSql calls.

Example / implementation direction

await using var tx = await db.Database.BeginTransactionAsync(ct);
// perform related changes
await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);

HMS exercise: Create an invoice and its line items atomically; test rollback.

7. Performance, pooling and alternatives

Why it exists. ORM convenience has a cost; use measurements to decide between tracking, compiled queries, bulk tools or Dapper.

Professional practice. Measure allocations and SQL first; use context pooling only with safe state handling and avoid premature compiled-query optimization.

Example / implementation direction

var query = EF.CompileAsyncQuery((HospitalDbContext c, long id) => c.Patients.Where(p => p.Id == id).Select(p => p.FullName));

HMS exercise: Benchmark a patient lookup and explain whether optimization is justified.

Module review checklist

  • Can you explain the problem this tool or pattern solves?
  • Can you implement it without copying a template blindly?
  • Have you tested success, invalid input, concurrency and failure paths?
  • Can you explain its security, performance and operational trade-offs?
