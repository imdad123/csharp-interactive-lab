MODULE 14 · PROFESSIONAL GUIDE

Performance, observability and resilience

Async I/O, caching, profiling, SQL tuning, rate limiting, health checks, structured logs, metrics, traces, OpenTelemetry and resilience pipelines.

Why this module matters: production systems fail when engineers know syntax but not data integrity, operational behavior, security boundaries or failure modes. Learn the reasoning, then implement each exercise in the HMS solution.

1. Async I/O and resource efficiency

Why it exists. Blocking threads while waiting on I/O reduces throughput under load.

Professional practice. Use async database/network APIs end-to-end, cancellation and bounded concurrency; avoid async void and sync-over-async.

Example / implementation direction

var patient = await db.Patients.SingleOrDefaultAsync(x => x.Id == id, ct);

HMS exercise: Profile a report endpoint and remove blocking calls.

2. Caching strategy and invalidation

Why it exists. Caching reduces repeated work but stale data and invalidation mistakes can become correctness bugs.

Professional practice. Choose cache by data volatility, use distributed cache for multi-instance apps and define invalidation ownership.

Example / implementation direction

builder.Services.AddStackExchangeRedisCache(o => o.Configuration = config.GetConnectionString("Redis"));

HMS exercise: Cache doctor directory data with a documented invalidation policy.

3. Resilience and outbound HTTP

Why it exists. External systems fail slowly and intermittently; naive calls can consume all request capacity.

Professional practice. Set timeouts, use resilience handlers with bounded retries/circuit breakers and avoid retrying non-idempotent operations blindly.

Example / implementation direction

builder.Services.AddHttpClient().AddStandardResilienceHandler();

HMS exercise: Protect appointment booking from an unreliable SMS dependency.

4. Health checks and service objectives

Why it exists. A process can be alive but unable to serve traffic because its database or dependencies are unavailable.

Professional practice. Separate liveness and readiness, expose dependency health carefully and define latency/error/availability SLOs.

Example / implementation direction

builder.Services.AddHealthChecks().AddDbContextCheck();
app.MapHealthChecks("/health/ready");

HMS exercise: Add readiness checks and define an appointment API latency objective.

5. Logs, metrics and distributed traces

Why it exists. A request crossing API, database and message broker needs a connected diagnostic story.

Professional practice. Use structured logs, low-cardinality metrics, trace context propagation and OpenTelemetry exporters.

Example / implementation direction

builder.Services.AddOpenTelemetry().WithTracing(t => t.AddAspNetCoreInstrumentation().AddHttpClientInstrumentation());

HMS exercise: Trace a booking request through API and reminder publishing.

Module review checklist

  • Can you explain the problem this tool or pattern solves?
  • Can you implement it without copying a template blindly?
  • Have you tested success, invalid input, concurrency and failure paths?
  • Can you explain its security, performance and operational trade-offs?
