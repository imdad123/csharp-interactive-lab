MODULE 06 · PROFESSIONAL GUIDE

DTOs, validation and error handling

Request/response contracts, DataAnnotations, FluentValidation, model binding, custom validation, ProblemDetails, exception handling and API conventions.

Why this module matters: production systems fail when engineers know syntax but not data integrity, operational behavior, security boundaries or failure modes. Learn the reasoning, then implement each exercise in the HMS solution.

1. Request DTOs and contract boundaries

Why it exists. Exposing EF entities couples clients to persistence and can leak fields or create over-posting vulnerabilities.

Professional practice. Define request and response DTOs for each use case; map explicitly and version contract changes.

Example / implementation direction

public sealed record CreatePatientRequest(string MedicalRecordNo,string FullName,DateOnly? DateOfBirth);

HMS exercise: Create separate create, update and response DTOs for patient records.

2. Validation at the API boundary

Why it exists. Invalid input should be rejected consistently before business operations; client-side validation alone is not trustworthy.

Professional practice. Use DataAnnotations for simple rules and FluentValidation for reusable or conditional rules; keep domain invariants in domain logic.

Example / implementation direction

RuleFor(x => x.FullName).NotEmpty().MaximumLength(160);
RuleFor(x => x.MedicalRecordNo).NotEmpty();

HMS exercise: Validate patient registration including conditional fields and database uniqueness.

3. Model binding and input parsing

Why it exists. HTTP data arrives as route, query, header and body values; parsing failures must become clear client errors.

Professional practice. Understand binding sources, nullable values, DateOnly/DateTimeOffset, enum parsing and custom binders when necessary.

Example / implementation direction

app.MapGet("/api/appointments", (DateOnly from, DateOnly to) => Results.Ok(new { from, to }));

HMS exercise: Validate date ranges and timezone assumptions for appointment searches.

4. Problem Details and exception handling

Why it exists. Ad hoc error JSON makes clients brittle and can disclose internal implementation details.

Professional practice. Use RFC 9457 Problem Details, centralized exception handling, stable error codes and safe trace identifiers.

Example / implementation direction

builder.Services.AddProblemDetails();
app.UseExceptionHandler();

HMS exercise: Return consistent 400, 404, 409 and 500 responses without stack traces.

5. Business validation and uniqueness races

Why it exists. A pre-check can improve user feedback but cannot guarantee uniqueness under concurrent requests.

Professional practice. Enforce unique constraints in SQL Server and translate expected constraint conflicts into safe 409 responses.

Example / implementation direction

try { db.Patients.Add(patient); await db.SaveChangesAsync(ct); } catch (DbUpdateException ex) when (IsUniqueViolation(ex)) { return Results.Conflict(); }

HMS exercise: Test two concurrent registrations using the same medical record number.

6. Validation testing and API conventions

Why it exists. Validation rules are part of the public contract and must be tested like business behavior.

Professional practice. Test invalid payloads, boundary values, malformed JSON, authorization and stable Problem Details shape.

Example / implementation direction

// Integration test: POST invalid patient payload; assert 400 and application/problem+json.

HMS exercise: Create integration tests for missing, oversized and malformed fields.

  • Can you implement it without copying a template blindly?
  • Have you tested success, invalid input, concurrency and failure paths?
  • Can you explain its security, performance and operational trade-offs?
