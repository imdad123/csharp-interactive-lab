MODULE 12 · PROFESSIONAL GUIDE

Microservices and distributed systems

Service boundaries, modular monolith first, synchronous communication, gRPC, messaging, outbox, sagas, idempotent consumers, API gateway and service discovery.

Why this module matters: production systems fail when engineers know syntax but not data integrity, operational behavior, security boundaries or failure modes. Learn the reasoning, then implement each exercise in the HMS solution.

1. Service boundaries and modular monolith first

Why it exists. Microservices add network failure, deployment, observability and data consistency costs; splitting too early makes delivery slower.

Professional practice. Find bounded contexts and ownership first; extract only modules with independent scaling, deployment or team needs.

Example / implementation direction

// Candidates: Scheduling, Billing, Pharmacy
// Keep shared contracts explicit; do not share EF entity assemblies.

HMS exercise: Map HMS bounded contexts and justify whether any requires a separate service.

2. Synchronous communication and gRPC

Why it exists. HTTP APIs are useful for external clients; gRPC can suit efficient internal service-to-service contracts.

Professional practice. Define timeouts, deadlines, retries only for safe operations, authentication and compatibility.

Example / implementation direction

// Define a protobuf service contract for internal availability lookup.

HMS exercise: Compare REST and gRPC for doctor availability and explain the trade-offs.

3. Messaging and eventual consistency

Why it exists. Asynchronous messaging decouples workloads but introduces duplicates, ordering and delayed visibility.

Professional practice. Use durable brokers, explicit message contracts, idempotent consumers and observable retry/dead-letter policies.

Example / implementation direction

public sealed record AppointmentBooked(Guid EventId,long AppointmentId,DateTimeOffset OccurredAt);

HMS exercise: Publish an appointment-booked event to trigger reminders without blocking booking.

4. Outbox and inbox patterns

Why it exists. Database commit and message publish are not one atomic operation; naive dual writes lose or duplicate events.

Professional practice. Write business data and outbox row in one DB transaction; publish later and deduplicate received messages.

Example / implementation direction

// Save appointment + OutboxMessage in the same SQL transaction;
// background dispatcher publishes pending rows.

HMS exercise: Guarantee reminder events are eventually published after appointment commit.

5. Sagas and distributed workflows

Why it exists. A workflow across services cannot rely on one SQL transaction; partial completion needs explicit compensation.

Professional practice. Model saga state, timeouts, retries and compensating actions; distinguish compensation from rollback.

Example / implementation direction

// Admission saga: reserve bed -> authorize deposit -> confirm admission;
// compensation: release reservation if payment fails.

HMS exercise: Design a multi-step admission workflow and test each failure point.

6. Gateway, discovery and deployment topology

Why it exists. Clients need a stable edge while services evolve independently; internal topology must remain observable.

Professional practice. Use a gateway for routing and cross-cutting edge policy, not as a dumping ground for business logic.

Example / implementation direction

// Gateway routes /api/scheduling/* to Scheduling service;
// service identity is authenticated independently.

HMS exercise: Draw the gateway and service topology for the HMS.

7. Distributed data and consistency

Why it exists. Independent services should own their data; cross-service joins and shared writes create hidden coupling.

Professional practice. Use API composition, projections and events; choose consistency windows explicitly for each workflow.

Example / implementation direction

// Billing owns invoices; Scheduling owns appointments;
// read model consumes AppointmentBooked events.

HMS exercise: Define source-of-truth ownership and read models for billing reports.

Module review checklist

  • Can you explain the problem this tool or pattern solves?
  • Can you implement it without copying a template blindly?
  • Have you tested success, invalid input, concurrency and failure paths?
  • Can you explain its security, performance and operational trade-offs?
