16 · HospitalApp.Console project

Apply the roadmap to one evolving hospital application, beginning with a console app before SQL Server and web APIs.

Study approach: Understand the problem first, then the concept, syntax, trade-offs, and its use in a real enterprise application.

Project rules

  • Console-first: learn the language and domain before a web framework.
  • Separate console input/output from business logic.
  • Use DTOs at boundaries and keep domain rules independently testable.
  • Add abstractions when they solve a real problem, not just to increase project count.
  • Introduce SQL Server after the in-memory/domain foundation is clear.

Stage 1 — Console fundamentals

  • Create HospitalApp.Console and a menu.
  • Register, list and search patients.
  • Validate input and handle errors.
  • Extract operations into methods.

Stage 2 — Collections and LINQ

  • Use List<Patient> and Dictionary<int,Patient>.
  • Add doctor and department collections.
  • Filter and sort appointments with LINQ.
  • Generate daily summaries.

Stage 3 — OOP, DTOs and domain rules

  • Create Patient, Doctor, Department, Appointment, Room, Bed and Invoice models.
  • Add constructors, encapsulated state and controlled state transitions.
  • Introduce interfaces for real service boundaries.
  • Use request DTOs for registration and booking.

Stage 4 — SQL Server and persistence

  • Design normalized schema with keys and constraints.
  • Write parameterized queries and stored procedures.
  • Connect using ADO.NET and map rows to DTOs.
  • Practice DataTable and DataRow.
  • Use transactions for invoice posting and bed allocation.

Stage 5 — Async and testing

  • Make I/O-bound repository calls asynchronous.
  • Pass CancellationToken through call chains.
  • Add configuration and structured logging.
  • Unit-test business rules and integration-test database operations.

Stage 6 — ASP.NET Core APIs

  • Create Minimal API endpoints for patients, doctors and appointments.
  • Use request/response DTOs and validation.
  • Configure DI lifetimes, authentication, authorization and error handling.
  • Document endpoints with OpenAPI and test API/database integration.

Stage 7 — Enterprise readiness

  • Add pagination, filtering and reporting endpoints.
  • Optimize important SQL with execution plans and Query Store.
  • Test concurrent booking and bed allocation.
  • Protect patient and financial data with authorization and audit trails.
  • Document deployment, backup, restore and monitoring.

Definition of done

A feature is complete when requirements and edge cases are clear, data integrity is protected, business logic is testable, SQL is parameterized, tests pass, failures are diagnosable, sensitive data is protected and performance has been considered.

Detailed capstone: build HospitalApp in professional stages

Build one hospital workflow in layers. Start console-first to master C# before SQL Server and web APIs.

Stage 1 — Console-first

Menus for patient registration, listing, searching and appointment booking. Use typed values, loops, methods, validation and in-memory collections. Keep console I/O in presentation code.

Stage 2 — Domain model

Create Patient, Doctor, Appointment and Invoice. Protect invariants: valid IDs, required names, no bookings for inactive patients and valid patient/doctor references. Prefer composition for relationships.

Stage 3 — Services and DTOs

Create RegisterPatientRequest, PatientResponse and AppointmentResponse. Services coordinate workflows; business rules remain independent of console and HTTP types.

Stage 4 — SQL Server

Design Patients, Doctors, Appointments, Invoices and InvoiceLines with keys and constraints. Start with parameterized ADO.NET, then EF Core for mapping, migrations, LINQ and transactions. Never concatenate untrusted input into SQL.

Stage 5 — Testing

Unit-test calculations and booking rules. Fake repository/notifier dependencies. Integration-test mappings and transactions. Add structured logging, cancellation and consistent error handling.

Stage 6 — ASP.NET Core API

Expose patient and appointment endpoints. Add DTO validation, authentication, role/policy authorization, OpenAPI and integration tests. Keep business rules in services/domain, not endpoint lambdas.

Stage 7 — Production readiness

Use environment settings and secret storage, least-privilege DB access, HTTPS, backups, monitoring, health checks, deployment automation and restore drills. Expose only data each role needs.

Suggested solution structure

HospitalApp.sln
src/ HospitalApp.Console/ HospitalApp.Domain/ HospitalApp.Application/
     HospitalApp.Infrastructure/ HospitalApp.Api/
tests/ HospitalApp.UnitTests/ HospitalApp.IntegrationTests/

Start smaller if needed: Console + Domain, then add layers as complexity grows. Architecture should clarify dependencies, not create empty projects prematurely.

Definition of done

  • Patient registration/retrieval validates input.
  • Booking enforces patient/doctor availability.
  • Invoice posting is atomic and auditable.
  • Business rules have unit tests; DB/API boundaries have integration tests.
  • Authorization prevents access outside user permissions.
  • Backups are proven by restore drills.
