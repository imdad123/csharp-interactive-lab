03 · Object-oriented programming

Model hospital business concepts with state, behavior, encapsulation and clear abstractions.

Study approach: Understand the problem first, then the concept, syntax, trade-offs, and its use in a real enterprise application.

Why OOP exists

As programs grow, unrelated data and procedures become hard to coordinate. Objects group related state and behavior; encapsulation protects valid state from arbitrary changes.

Classes, objects and constructors

  • A class defines a type; an object is an instance.
  • Fields store internal state; properties expose controlled access.
  • Constructors establish required initial state and can chain to avoid duplicated setup.
  • Object initializers are convenient for optional values but should not bypass invariants.
public class Patient
{
    public int Id { get; }
    public string Name { get; private set; }

    public Patient(int id, string name)
    {
        Id = id;
        Rename(name);
    }

    public void Rename(string name)
    {
        if (string.IsNullOrWhiteSpace(name))
            throw new ArgumentException("Name is required.");
        Name = name.Trim();
    }
}

Encapsulation and controlled updates

Do not expose public setters for values that must obey business rules. Prefer methods such as Reschedule, Cancel, Complete or AllocateBed so the object can enforce valid transitions.

Inheritance and polymorphism

Inheritance models an “is-a” relationship. Virtual and abstract members allow specialization; polymorphism lets callers work through a common base type. Derived classes must honor the base contract. Do not use inheritance only to reuse a few lines of code.

Interfaces and composition

Interfaces define capabilities or contracts. Composition combines collaborating objects and is often preferable to inheritance. For example, AppointmentService can depend on an IAppointmentRepository and INotificationSender without being a kind of either.

Members and access modifiers

  • public, private, protected, internal, protected internal, private protected.
  • static belongs to the type; readonly is assigned at declaration or constructor; const is compile-time constant.
  • sealed prevents further inheritance/overriding where appropriate.
  • Understand object equality, ToString, Equals and GetHashCode.

HospitalApp practice

Create Patient, Doctor, Department, Appointment, Room, Bed and Invoice models. Protect appointment state using methods. Use interfaces for service boundaries and composition for scheduling and billing collaborators.

Deep dive: OOP in a hospital system

OOP keeps related data and behavior together. Without it, a large application becomes unrelated variables and long methods that are difficult to change safely.

Class, object and encapsulation

public class Patient
{
    public int Id { get; }
    public string Name { get; private set; }
    public bool IsActive { get; private set; }
    public Patient(int id, string name)
    {
        if (id <= 0) throw new ArgumentOutOfRangeException(nameof(id));
        if (string.IsNullOrWhiteSpace(name)) throw new ArgumentException("Name required");
        Id = id; Name = name; IsActive = true;
    }
    public void Deactivate() => IsActive = false;
}

The constructor establishes valid state. A private setter prevents unrelated code changing activity without the domain operation.

Inheritance versus composition

A ConsultantDoctor may be a Doctor (is-a). An Appointment is not a Patient. An Appointment has a Patient and Doctor (has-a), so composition is the correct relationship.

public class Appointment
{
    public int Id { get; }
    public Patient Patient { get; }
    public Doctor Doctor { get; }
    public DateTime ScheduledAt { get; }
    public Appointment(int id, Patient patient, Doctor doctor, DateTime at)
        => (Id, Patient, Doctor, ScheduledAt) = (id, patient, doctor, at);
}

Interfaces and polymorphism

public interface IPaymentMethod
{
    Task<PaymentResult> PayAsync(decimal amount, CancellationToken ct);
}
public sealed class CashPayment : IPaymentMethod
{
    public Task<PaymentResult> PayAsync(decimal amount, CancellationToken ct)
        => Task.FromResult(PaymentResult.Accepted(amount));
}

Invoice processing can depend on IPaymentMethod instead of hard-coding cash, card or another approved payment provider. The same contract supports different implementations.

Access modifiers and design judgment

Public is an external contract; private hides implementation; protected is available to derived types; internal limits access to the assembly. Prefer the narrowest access. A tiny calculation does not need a class hierarchy. Avoid one class per noun without a responsibility.

Worked examples: object-oriented programming

Classes and objects

public sealed class Patient
{
    public int Id { get; set; }
    public string Name { get; set; } = "";
}

var patient = new Patient { Id = 101, Name = "Amina Khan" };
Console.WriteLine(patient.Name);

A class defines a reference type; an object is an instance. A class can contain state, behavior and rules. Keep business rules close to the data they protect when that makes the model easier to reason about.

Constructors and constructor validation

public sealed class MedicalRecord
{
    public int Id { get; }
    public string Mrn { get; }

    public MedicalRecord(int id, string mrn)
    {
        if (id <= 0) throw new ArgumentOutOfRangeException(nameof(id));
        if (string.IsNullOrWhiteSpace(mrn))
            throw new ArgumentException("MRN is required.", nameof(mrn));

        Id = id;
        Mrn = mrn.Trim();
    }
}

var record = new MedicalRecord(1001, "MR-001");

Encapsulation: protect invariants

public sealed class Invoice
{
    private readonly List<InvoiceLine> _lines = [];

    public IReadOnlyList<InvoiceLine> Lines => _lines.AsReadOnly();
    public decimal Total => _lines.Sum(line => line.Amount);

    public void AddLine(string description, decimal amount)
    {
        if (string.IsNullOrWhiteSpace(description))
            throw new ArgumentException("Description is required.");
        if (amount <= 0)
            throw new ArgumentOutOfRangeException(nameof(amount));

        _lines.Add(new InvoiceLine(description, amount));
    }
}

public sealed record InvoiceLine(string Description, decimal Amount);

Methods, parameters and return values

public static class BillingCalculator
{
    public static decimal CalculateBalance(
        decimal invoiceTotal,
        decimal amountPaid)
    {
        if (invoiceTotal < 0 || amountPaid < 0)
            throw new ArgumentOutOfRangeException();

        return invoiceTotal - amountPaid;
    }
}

decimal balance = BillingCalculator.CalculateBalance(5000m, 2000m);

Method overloading

public static class PatientSearch
{
    public static string Normalize(string mrn)
        => mrn.Trim().ToUpperInvariant();

    public static string Normalize(string hospitalCode, string mrn)
        => $"{hospitalCode.Trim().ToUpperInvariant()}-{Normalize(mrn)}";
}

string key1 = PatientSearch.Normalize(" mr-01 ");
string key2 = PatientSearch.Normalize("GH", " mr-01 ");

Overloads share a name but differ by parameter list. Return type alone cannot distinguish overloads. Avoid overload sets that make calls ambiguous, especially when optional parameters are involved.

Access modifiers

public class PatientService
{
    private readonly string _connectionName = "HospitalDb";
    protected void WriteAudit(string action) { /* shared with derived classes */ }
    internal void RebuildIndex() { /* same assembly only */ }
    public void Register() { /* public contract */ }
}

Use the least permissive visibility that supports the design. private protected, protected internal and nested-type visibility are additional tools; do not expose internal implementation details by default.

Properties and backing fields

public sealed class PatientProfile
{
    private string _fullName = "";

    public string FullName
    {
        get => _fullName;
        set
        {
            if (string.IsNullOrWhiteSpace(value))
                throw new ArgumentException("Name is required.");
            _fullName = value.Trim();
        }
    }
}

Use an auto-property for simple storage. Use a backing field when validation, normalization, notifications or lazy computation is needed. A property is an API surface, not merely a public field.

Value types versus reference types

int originalAge = 30;
int copiedAge = originalAge;
copiedAge++;
Console.WriteLine(originalAge); // 30

var originalPatient = new PatientProfile { FullName = "Amina" };
var secondReference = originalPatient;
secondReference.FullName = "Sara";
Console.WriteLine(originalPatient.FullName); // Sara

Value assignment copies the value. Reference assignment copies a reference to the same object. Structs are value types; classes are reference types. Avoid oversimplifying this as “all value types are on the stack and all reference types are on the heap”—storage depends on context and implementation.

Inheritance and base behavior

public abstract class Person
{
    protected Person(string name) => Name = name;
    public string Name { get; }
}

public sealed class Doctor : Person
{
    public string Specialty { get; }

    public Doctor(string name, string specialty) : base(name)
        => Specialty = specialty;
}

var doctor = new Doctor("Dr. Sara", "Cardiology");

Composition and association

public sealed class Appointment
{
    public PatientProfile Patient { get; }
    public Doctor Doctor { get; }
    public DateTime StartsAt { get; }

    public Appointment(PatientProfile patient, Doctor doctor, DateTime startsAt)
    {
        Patient = patient;
        Doctor = doctor;
        StartsAt = startsAt;
    }
}

An appointment is associated with a patient and doctor. Composition means an object owns or coordinates other objects; inheritance means an “is-a” relationship. Prefer composition when a type needs collaborators rather than pretending one type is a subtype of another.

Polymorphism and virtual dispatch

public abstract class Notification
{
    public abstract Task SendAsync(string message, CancellationToken ct);
}

public sealed class EmailNotification : Notification
{
    public override Task SendAsync(string message, CancellationToken ct)
    {
        Console.WriteLine($"Email: {message}");
        return Task.CompletedTask;
    }
}

public sealed class SmsNotification : Notification
{
    public override Task SendAsync(string message, CancellationToken ct)
    {
        Console.WriteLine($"SMS: {message}");
        return Task.CompletedTask;
    }
}

Notification channel = new SmsNotification();
await channel.SendAsync("Appointment confirmed", CancellationToken.None);

Abstract classes and methods

public abstract class Report
{
    public string Title { get; init; } = "";
    public abstract string Generate();

    public void Print()
        => Console.WriteLine($"{Title}\n{Generate()}");
}

public sealed class DailyCollectionReport : Report
{
    public decimal Total { get; init; }
    public override string Generate() => $"Collected: {Total:N2}";
}

Interfaces and multiple capabilities

public interface IAuditable
{
    DateTime CreatedAtUtc { get; }
}

public interface IArchivable
{
    void Archive();
}

public sealed class PatientDocument : IAuditable, IArchivable
{
    public DateTime CreatedAtUtc { get; } = DateTime.UtcNow;
    public bool IsArchived { get; private set; }
    public void Archive() => IsArchived = true;
}

Use interfaces to describe capabilities and boundaries. A class can implement multiple interfaces, while it can inherit from only one class. Keep interfaces cohesive and avoid creating one interface for every class without a useful substitution or testing boundary.

When to choose class, record, struct or interface

  • class: identity and mutable lifecycle, such as a tracked patient entity.
  • record class: value-like data and equality by contents, such as an API response.
  • struct: small value with value semantics, such as a coordinate or measurement, when profiling and semantics support it.
  • interface: capability/contract boundary, such as IPatientRepository.
