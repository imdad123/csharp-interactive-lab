04 · Generics, DTOs and architecture

Write reusable type-safe code and separate domain rules from UI and infrastructure.

Study approach: Understand the problem first, then the concept, syntax, trade-offs, and its use in a real enterprise application.

Why generics exist

Generics make reusable containers and algorithms work with different types without losing compile-time type safety. They avoid object-based storage and repetitive casting.

public class Repository<T>
{
    private readonly List<T> _items = new();
    public void Add(T item) => _items.Add(item);
    public IReadOnlyList<T> GetAll() => _items;
}

Generic constraints and variance

Learn where T : class, struct, notnull, new(), or an interface/base type. Constraints express what operations a generic type can safely perform. Understand covariance (out) and contravariance (in) when consuming generic interfaces and delegates.

DTOs and why they matter

A Data Transfer Object carries data across a boundary such as a form, API or service. It prevents business methods from depending on UI controls and avoids exposing database entities as public contracts. DTOs also make unit tests straightforward: construct the input object and call the method.

public sealed record RegisterPatientRequest(
    string Name, DateOnly DateOfBirth, string PhoneNumber);

public Patient Register(RegisterPatientRequest request)
{
    // Validate and apply business rules.
    return new Patient(request.Name);
}

SOLID principles

  • Single Responsibility: one coherent reason to change.
  • Open/Closed: extend stable behavior without constantly modifying it.
  • Liskov Substitution: derived types honor base expectations.
  • Interface Segregation: focused contracts beat oversized interfaces.
  • Dependency Inversion: high-level policy should not depend on low-level implementation details.

Dependency injection and architecture

Constructor injection makes dependencies explicit and testable. Separate domain rules, application use cases, infrastructure and delivery mechanisms when the complexity justifies it. Repository abstractions can protect meaningful boundaries; unnecessary interfaces create indirection without value.

HospitalApp practice

  1. Create RegisterPatientRequest and BookAppointmentRequest DTOs.
  2. Keep validation independent of Console.ReadLine and HTTP.
  3. Inject repository abstractions into application services.
  4. Unit-test service behavior by constructing DTOs directly.

Deep dive: generics, DTOs, SOLID and dependency injection

Generics remove duplication with type safety

Patient, Doctor and Invoice repositories share mechanics. Generics can reuse algorithms while preserving compile-time types.

public interface IEntity { int Id { get; } }
public class InMemoryRepository<T> where T : IEntity
{
    private readonly List<T> _items = [];
    public void Add(T item) => _items.Add(item);
    public T? GetById(int id) => _items.FirstOrDefault(x => x.Id == id);
}

The constraint guarantees T exposes Id. Do not automatically build a generic repository for every EF Core project: DbContext and DbSet already provide unit-of-work/repository-like behavior. Add abstractions when they create a useful boundary.

DTOs separate transport from domain

WebForms, mobile and APIs may send different fields. A DTO defines exactly what crosses a boundary and prevents a client from posting protected entity fields such as IsAdmin or account balance.

public sealed record RegisterPatientRequest(
    string Name, DateOnly DateOfBirth, string PhoneNumber);
public sealed record PatientResponse(
    int Id, string MedicalRecordNumber, string Name);

Validate request, map to domain model, persist, then map to response. A DTO is not automatically a domain entity.

SOLID with hospital examples

  • Single Responsibility: registration registers patients; receipt formatting belongs elsewhere.
  • Open/Closed: add another notifier without rewriting registration.
  • Liskov: implementations honor the behavior promised by their interface.
  • Interface Segregation: use IAppointmentNotifier rather than one giant IHospitalService.
  • Dependency Inversion: business workflows depend on abstractions, not a specific SMS vendor SDK.

Dependency injection

public interface IAppointmentNotifier
{
    Task SendConfirmationAsync(int appointmentId, CancellationToken ct);
}
public sealed class AppointmentService(IAppointmentNotifier notifier)
{
    public Task ConfirmAsync(int id, CancellationToken ct)
        => notifier.SendConfirmationAsync(id, ct);
}
builder.Services.AddScoped<AppointmentService>();
builder.Services.AddScoped<IAppointmentNotifier, SmsAppointmentNotifier>();

Scoped suits request-oriented services using a scoped DbContext; Singleton is for safe shared services; Transient creates a new instance each resolution. Never inject a scoped DbContext into a singleton.

Worked examples: generics and application design

Generic method

static void PrintItems<T>(IEnumerable<T> items)
{
    foreach (T item in items)
        Console.WriteLine(item);
}

PrintItems(new[] { 10, 20, 30 });
PrintItems(new[] { "Cardiology", "Emergency" });

Generics let one algorithm work with multiple types while preserving compile-time type safety. They avoid repeated implementations and unsafe casts.

Generic class

public sealed class ApiResult<T>
{
    public bool Success { get; init; }
    public T? Data { get; init; }
    public string? Error { get; init; }

    public static ApiResult<T> Ok(T data)
        => new() { Success = true, Data = data };

    public static ApiResult<T> Fail(string error)
        => new() { Success = false, Error = error };
}

ApiResult<int> patientIdResult = ApiResult<int>.Ok(1205);
ApiResult<string> nameResult = ApiResult<string>.Ok("Amina");

Generic constraints

static T Create<T>() where T : new()
    => new T();

public interface IEntity
{
    int Id { get; }
}

static int GetId<T>(T entity) where T : IEntity
    => entity.Id;

Constraints tell the compiler what operations are safe. Common constraints include class, class?, struct, notnull, interface/base-class constraints and new(). Choose the narrowest constraint that expresses the requirement.

Generic repository contract

public interface IReadRepository<TEntity, in TKey>
    where TEntity : class
{
    Task<TEntity?> FindAsync(TKey id, CancellationToken ct);
    Task<IReadOnlyList<TEntity>> GetAllAsync(CancellationToken ct);
}

Generic repositories can reduce repetitive CRUD plumbing, but they can also hide important query behavior and database capabilities. For EF Core, a focused application query/service can be clearer than a universal repository with dozens of methods.

Concrete repository implementation

public sealed class PatientReadRepository(HospitalDbContext db)
    : IReadRepository<Patient, int>
{
    public Task<Patient?> FindAsync(int id, CancellationToken ct)
        => db.Patients.AsNoTracking()
            .SingleOrDefaultAsync(p => p.Id == id, ct);

    public async Task<IReadOnlyList<Patient>> GetAllAsync(CancellationToken ct)
        => await db.Patients.AsNoTracking()
            .OrderBy(p => p.FullName)
            .ToListAsync(ct);
}

Service pattern and business workflow

public sealed class RegisterPatientService(IPatientRepository repository)
{
    public async Task<int> ExecuteAsync(
        RegisterPatientCommand command,
        CancellationToken ct)
    {
        if (string.IsNullOrWhiteSpace(command.FullName))
            throw new ArgumentException("Patient name is required.");

        if (await repository.MrnExistsAsync(command.Mrn, ct))
            throw new InvalidOperationException("MRN already exists.");

        var patient = new PatientEntity
        {
            MedicalRecordNumber = command.Mrn.Trim(),
            FullName = command.FullName.Trim()
        };

        await repository.AddAsync(patient, ct);
        return patient.Id;
    }
}

public sealed record RegisterPatientCommand(string Mrn, string FullName);

SOLID: single responsibility and dependency inversion

public interface IReceiptSender
{
    Task SendAsync(string recipient, string receipt, CancellationToken ct);
}

public sealed class InvoiceService(IReceiptSender sender)
{
    public async Task FinalizeAsync(Invoice invoice, CancellationToken ct)
    {
        invoice.MarkFinalized();
        await sender.SendAsync(invoice.PatientEmail, invoice.ToText(), ct);
    }
}

The invoice workflow depends on an abstraction rather than a concrete SMTP client. A separate implementation handles email delivery. This also makes the workflow easier to test.

Open/closed and strategy example

public interface IDiscountPolicy
{
    decimal Calculate(decimal subtotal);
}

public sealed class SeniorDiscount : IDiscountPolicy
{
    public decimal Calculate(decimal subtotal) => subtotal * 0.10m;
}

public sealed class NoDiscount : IDiscountPolicy
{
    public decimal Calculate(decimal subtotal) => 0m;
}

static decimal GetPayable(decimal subtotal, IDiscountPolicy policy)
    => subtotal - policy.Calculate(subtotal);

Dependency injection without a web framework

using Microsoft.Extensions.DependencyInjection;

var services = new ServiceCollection();
services.AddSingleton<IClock, SystemClock>();
services.AddTransient<AppointmentReminderService>();

using var provider = services.BuildServiceProvider();
var reminder = provider.GetRequiredService<AppointmentReminderService>();

This demonstrates the DI container in a console process. ASP.NET Core uses the same Microsoft.Extensions.DependencyInjection abstractions and registers the service provider through its host.

Clean Architecture dependency direction

src/
  Hospital.Domain/          # entities and domain rules
  Hospital.Application/     # use cases and interfaces
  Hospital.Infrastructure/  # SQL Server, email, external services
  Hospital.Console/         # console entry point / composition root
tests/
  Hospital.UnitTests/
  Hospital.IntegrationTests/

Dependencies point inward: Infrastructure implements interfaces defined by Application; Domain should not depend on EF Core, ASP.NET Core or a database provider. Keep this architecture proportional to the system size.
