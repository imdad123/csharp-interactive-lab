GIT · MODULE 01

Core Git concepts

Git records project history as a sequence of commits. It lets you inspect, compare and restore changes rather than relying on folders named final-final-v3.

The three areas to understand

  • Working tree: files you are currently editing.
  • Staging area/index: the exact changes selected for the next commit.
  • Repository: committed history stored in .git.
git init
git status
git add src/PatientService.cs
git diff --staged
git commit -m "feat: add patient registration service"

Staging is important because one working directory may contain several unrelated edits. Select only the coherent change you intend to record.

Inspect history

git log --oneline --graph --decorate --all
git show HEAD
git diff
git diff --staged

Use diff before committing to review what changed. Commit messages should explain intent, not merely say update.

Ignore generated and secret files

# .gitignore
/vendor/
/node_modules/
.env
*.log
bin/
obj/
.vs/

Ignore build output and local secrets, but do not ignore source, migrations or lock files needed by the team. If a secret was committed, deleting it in a later commit does not make it safe; rotate it immediately.

Hospital HMS workflow example

git status
git add src/Patients/PatientService.cs tests/PatientServiceTests.cs
git diff --staged
git commit -m "feat(patient): validate patient registration"

Keep a commit focused: a patient registration feature should not also contain unrelated CSS formatting and database backup files.

Practice task

  1. Initialize a repository for a sample HMS.
  2. Add README, source and tests.
  3. Create a .gitignore for IDE/build files and local secrets.
  4. Make two separate commits for two unrelated changes.
  5. Use log, show and diff to inspect the history.
