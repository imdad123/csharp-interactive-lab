Phase 6 — Exception Handling and Debugging

Complete topic-by-topic reference with explanations, syntax and practical Hospital Management System examples.

1. What are exceptions?

Exceptions signal failures that interrupt normal control flow. Use them for exceptional failures, not ordinary validation branches that callers can reasonably handle as results.

throw new InvalidOperationException("Invoice is already finalized.");

2. Exception hierarchy

All exceptions derive from System.Exception. Catch specific exception types before broader types; avoid catching Exception unless at a boundary where you can log and translate safely.

try { await SaveAsync(ct); }
catch (DbUpdateException ex) { logger.LogError(ex, "Database update failed"); throw; }

3. Try, Catch and Finally

try contains risky work; catch handles selected failures; finally runs cleanup regardless of success or failure. Prefer using for disposable resources.

try { ProcessPayment(); }
catch (PaymentGatewayException ex) { Log(ex); }
finally { CloseSession(); }

4. Multiple catch blocks

Multiple catch blocks handle different failure categories. Order them from most specific to most general.

try { Import(); }
catch (FileNotFoundException) { Console.WriteLine("File missing"); }
catch (UnauthorizedAccessException) { Console.WriteLine("Access denied"); }
catch (IOException ex) { Log(ex); }

5. Exception filters

Filters use when to decide whether a catch block should handle an exception. They can inspect context without nesting another if.

catch (HttpRequestException ex) when (ex.StatusCode == HttpStatusCode.NotFound)
{
    return null;
}

6. Throw vs Throw ex

throw; rethrows the current exception and preserves its stack trace. throw ex; resets the apparent throw location and should generally be avoided.

catch (Exception)
{
    LogFailure();
    throw; // preserve original stack
}

7. Inner exceptions

InnerException preserves the underlying cause when wrapping an exception with higher-level context.

try { await repository.SaveAsync(entity, ct); }
catch (DbException ex)
{
    throw new PatientPersistenceException("Could not save patient.", ex);
}

8. Custom exceptions

Custom exception types represent meaningful failure categories that callers can distinguish. Keep them focused and preserve inner exceptions.

public sealed class AppointmentConflictException(string message) : Exception(message);

9. Global exception handling concepts

An application boundary can translate unhandled exceptions into consistent logs and safe error responses. Never expose stack traces, secrets or database details to clients.

app.UseExceptionHandler(); // configure a production exception handler/problem-details response

10. When to catch and when to propagate

Catch only when you can recover, add useful context, translate to a boundary response or perform required compensation. Otherwise propagate and let the owning boundary handle it.

try { await BookAsync(ct); }
catch (AppointmentConflictException) { return BookingResult.Conflict(); }
// unexpected exceptions propagate

11. IDisposable

IDisposable provides deterministic cleanup for resources such as streams, handles and connections. Dispose resources you own; do not manually dispose injected dependencies unless ownership is yours.

using var stream = File.OpenRead("patients.json");

12. Using statement

A using statement scopes disposal to a block and guarantees cleanup when control exits the block.

using (var connection = new SqlConnection(connectionString))
{
    await connection.OpenAsync(ct);
}

13. Using declarations

A using declaration disposes at the end of the containing scope, reducing indentation while preserving deterministic cleanup.

using var reader = new StreamReader(path);
string content = await reader.ReadToEndAsync(ct);

14. Debugging in Visual Studio

The debugger lets you pause execution, inspect state and step through code. Debug the failing behavior at the point where assumptions stop being true.

// Set a breakpoint here and inspect patientId and request.
var patient = await service.FindAsync(patientId, ct);

15. Breakpoints

Breakpoints pause execution at a line so you can inspect the call and local state. Conditional breakpoints pause only when an expression is true.

// Conditional breakpoint condition: patientId == 1205
var patient = await repository.FindAsync(patientId, ct);

16. Conditional breakpoints

Conditional breakpoints are useful when a bug occurs only for one record or one loop iteration. Keep conditions simple and side-effect free.

// Break only for overdue invoices:
if (invoice.DueDate < DateOnly.FromDateTime(DateTime.Today)) Process(invoice);

17. Watch and Immediate windows

Watch evaluates selected expressions during debugging; Immediate executes expressions in the current debug context. Avoid changing production-like state unintentionally.

// Watch: invoice.Total
// Immediate: invoice.Lines.Count

18. Call Stack

The call stack shows the active chain of method calls and helps locate the caller that supplied invalid data or entered the failing path.

static void Register() => Validate();
static void Validate() => throw new InvalidOperationException("Invalid MRN");

19. Exception settings

Visual Studio exception settings control whether the debugger breaks when an exception is thrown, even if code later catches it. Use this to find the original throw site.

// Debug > Windows > Exception Settings
try { ParsePatientId(input); } catch (FormatException) { /* validation response */ }

20. Debugging complex applications

For distributed or asynchronous systems, correlate logs with trace IDs, inspect async call stacks, use structured logs and reproduce with controlled test data.

using var scope = logger.BeginScope(new Dictionary<string, object> { ["CorrelationId"] = correlationId });
logger.LogInformation("Processing appointment {AppointmentId}", appointmentId);
