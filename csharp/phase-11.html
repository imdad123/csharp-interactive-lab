Phase 11 — Memory Management, Runtime and Performance

Advanced C# and .NET library knowledge for engineers building reliable, high-throughput ASP.NET Core systems. Each topic explains the problem, shows practical code and gives you an implementation task.

Professional rule: understand correctness first, then measure performance. Do not add concurrency, unsafe code, pooling or complex abstractions without a concrete requirement and evidence.

TOPIC 01

Managed memory and the garbage collector

Why this matters

The GC reclaims unreachable managed objects. Understanding allocation and object lifetime helps diagnose memory pressure in long-running services.

Code example

var names = new List<string>();
for (var i = 0; i < 1000; i++) names.Add($"Patient-{i}");
// Observe allocations and collections with a profiler.

What you must practise

Profile an API endpoint under load and identify allocation hot spots before optimizing.

TOPIC 02

Generations and large object heap

Why this matters

The GC uses generations because most objects die young. Large objects are treated differently and can increase fragmentation and pause costs.

Code example

byte[] largeBuffer = new byte[100_000];
Console.WriteLine(GC.GetGeneration(largeBuffer));

What you must practise

Learn Gen 0/1/2, LOH thresholds, allocation rates and why pooling large buffers can help only when measured.

TOPIC 03

Finalizers and deterministic cleanup

Why this matters

Finalizers are nondeterministic and run only when the GC schedules them. IDisposable is the normal deterministic resource cleanup mechanism.

Code example

public sealed class FileLease : IDisposable
{
    private readonly FileStream _stream;
    public FileLease(string path) => _stream = File.OpenRead(path);
    public void Dispose() => _stream.Dispose();
}

What you must practise

Implement IDisposable around a resource and explain why finalizers should be rare and carefully designed.

TOPIC 04

IDisposable ownership and async disposal

Why this matters

Resource ownership must be explicit. The component that creates a disposable resource normally owns its disposal unless ownership is transferred.

Code example

await using var connection = new SqlConnection(connectionString);
await connection.OpenAsync(ct);

What you must practise

Trace ownership of streams, database connections and DI-managed services. Avoid disposing dependencies you do not own.

TOPIC 05

Span and ReadOnlySpan

Why this matters

Span represents a contiguous region of memory without requiring a new array. It is useful for allocation-sensitive parsing and slicing.

Code example

ReadOnlySpan<char> code = "MR-2026-0042";
ReadOnlySpan<char> prefix = code[..2];
Console.WriteLine(prefix);

What you must practise

Parse identifiers with spans and benchmark against Substring. Learn ref struct restrictions.

TOPIC 06

Memory and ReadOnlyMemory

Why this matters

Memory can represent memory across async boundaries where Span cannot be stored. It is useful for asynchronous APIs that operate on buffers.

Code example

public async Task WriteAsync(ReadOnlyMemory<byte> data, Stream stream, CancellationToken ct)
    => await stream.WriteAsync(data, ct);

What you must practise

Build an async buffer-processing method and understand ownership: the caller must not mutate the buffer while the operation uses it.

TOPIC 07

ArrayPool and object pooling

Why this matters

Pooling reuses buffers or objects to reduce allocations in hot paths. Pooled data must be returned and sensitive contents may need clearing.

Code example

byte[] rented = ArrayPool<byte>.Shared.Rent(8192);
try { await stream.ReadAsync(rented.AsMemory(0, 8192), ct); }
finally { ArrayPool<byte>.Shared.Return(rented, clearArray: true); }

What you must practise

Use ArrayPool in a benchmarked high-throughput scenario. Verify return happens on exceptions and sensitive data is cleared.

TOPIC 08

BenchmarkDotNet and microbenchmarking

Why this matters

Performance assumptions should be measured. Microbenchmarks compare isolated operations but do not replace production profiling.

Code example

[MemoryDiagnoser]
[Benchmark]
public string BuildName() => string.Concat("Patient", "-", 1205);

What you must practise

Create benchmarks for two mapping or parsing approaches. Run in Release mode and interpret allocation results.

TOPIC 09

dotnet-counters and runtime metrics

Why this matters

Runtime counters expose allocation rate, GC activity, thread-pool behavior and exception counts while an application runs.

Code example

// Terminal:
// dotnet-counters monitor --process-id <PID> System.Runtime

What you must practise

Run an API under load and correlate allocation rate, GC heap size and thread-pool queue length.

TOPIC 10

dotnet-trace and EventPipe

Why this matters

Tracing captures runtime and application events for deeper diagnosis of CPU, GC and contention issues.

Code example

// Terminal:
// dotnet-trace collect --process-id <PID> --providers Microsoft-Windows-DotNETRuntime

What you must practise

Capture a trace during a slow report operation and identify whether time is spent in CPU, GC or waiting.

TOPIC 11

DiagnosticSource and Activity

Why this matters

Activity represents a unit of work and supports distributed tracing. DiagnosticSource publishes instrumentation events consumed by observability tools.

Code example

using var activity = new Activity("HMS.GenerateInvoice").Start();
activity?.SetTag("invoice.id", invoiceId);

What you must practise

Add useful trace attributes without putting patient names, medical details or other sensitive data into telemetry.

TOPIC 12

Assembly loading and AssemblyLoadContext

Why this matters

The runtime loads assemblies and resolves dependencies. AssemblyLoadContext enables isolation scenarios such as plugin systems.

Code example

Assembly assembly = typeof(PatientService).Assembly;
Console.WriteLine(assembly.GetName().Name);

What you must practise

Inspect assembly metadata and understand dependency resolution. Study collectible load contexts before building plugin unload support.

TOPIC 13

Unsafe code and pointers

Why this matters

Unsafe code permits pointer operations and can interoperate with native libraries, but bypasses important runtime safety guarantees.

Code example

unsafe
{
    int value = 42;
    int* pointer = &value;
    Console.WriteLine(*pointer);
}

What you must practise

Understand fixed, pointers, bounds safety and when unsafe code is justified. Do not use it for ordinary CRUD APIs.

TOPIC 14

P/Invoke and native interop

Why this matters

Some systems expose native libraries rather than managed APIs. Platform invocation allows managed code to call native functions with careful ABI and memory rules.

Code example

[DllImport("kernel32.dll", SetLastError = true)]
static extern uint GetTickCount();

What you must practise

Study marshalling, calling conventions, native ownership and cross-platform limitations. Use source-generated LibraryImport where appropriate.

TOPIC 15

Source generators and compile-time code generation

Why this matters

Source generators inspect compilation inputs and emit C# during build. They can remove repetitive code and avoid some runtime reflection costs.

Code example

// Example attribute-driven generation concept:
[GenerateMapper]
public partial class PatientMapper { }

What you must practise

Understand IIncrementalGenerator, diagnostics, generated files and debugging generators. Build a small generator for repetitive DTO mapping.

TOPIC 16

Native AOT and trimming awareness

Why this matters

Trimming removes unused code and Native AOT compiles ahead of time. Reflection-heavy patterns and dynamic loading can require explicit preservation.

Code example

// Publish experiment:
// dotnet publish -c Release -r linux-x64 -p:PublishAot=true

What you must practise

Build a small AOT-compatible console app, inspect warnings and learn which reflection patterns need annotations or alternatives.
