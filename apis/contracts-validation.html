API ENGINEERING GUIDE 02

Contracts, validation and errors

DTOs, binding, validation, Problem Details, OpenAPI and compatibility. These guides focus specifically on designing APIs as stable, secure products for other software to consume.

API design principle: an API is a long-lived contract. Design for clients you do not control, handle failure explicitly, protect every resource and preserve compatibility deliberately.

TOPIC 01

Request and response DTOs

Why this matters

DTOs prevent over-posting and keep internal persistence models separate from public API contracts.

What you must learn

Learn request DTOs, response DTOs, immutable records, nested DTOs, mapping, required fields and contract evolution.

Code example

public sealed record CreateDoctorRequest(
    [property: Required, StringLength(100)] string FullName,
    [property: EmailAddress] string? Email);

public sealed record DoctorResponse(Guid Id, string FullName);

Practice task

Create different DTOs for create, update, list and detail operations. Confirm internal salary or security fields never appear in responses.

TOPIC 02

Model binding and validation

Why this matters

Model binding converts route, query, header and body data into .NET values. Validation rejects malformed or incomplete requests before business processing.

What you must learn

Learn binding sources, `[FromRoute]`, `[FromQuery]`, `[FromBody]`, DataAnnotations, FluentValidation, custom validators and validation error shape.

Code example

public sealed class CreateAppointmentRequest
{
    [Required] public Guid PatientId { get; init; }
    [Required] public Guid DoctorId { get; init; }
    [Required] public DateTimeOffset StartsAtUtc { get; init; }
}

Practice task

Test missing fields, malformed GUIDs, invalid dates and business conflicts separately.

TOPIC 03

Problem Details and exception mapping

Why this matters

A consistent error schema lets clients handle errors safely. Production responses must not expose stack traces, SQL details or secrets.

What you must learn

Learn RFC 9457 Problem Details, validation problem details, exception handlers, trace IDs and mapping domain errors to HTTP status codes.

Code example

builder.Services.AddProblemDetails();
builder.Services.AddExceptionHandler<GlobalExceptionHandler>();
app.UseExceptionHandler();

Practice task

Return 409 for a booking conflict, 404 for a missing patient and generic 500 for unexpected exceptions. Include a trace identifier.

TOPIC 04

OpenAPI and API explorer

Why this matters

OpenAPI is a machine-readable API description used by client generators, test tools and documentation portals.

What you must learn

Learn operation IDs, schemas, request/response examples, security schemes, tags, XML comments and Scalar or Swagger UI.

Code example

builder.Services.AddOpenApi();
var app = builder.Build();
if (app.Environment.IsDevelopment()) app.MapOpenApi();

Practice task

Review the generated document. Ensure error responses, authentication and validation are represented accurately.

TOPIC 05

API versioning and compatibility

Why this matters

Clients are not all upgraded at once. Versioning and compatibility policies prevent new releases from unexpectedly breaking older clients.

What you must learn

Learn URL/header/media-type versioning, additive changes, breaking changes, deprecation, sunset communication and contract tests.

Code example

[ApiController]
[Route("api/v1/doctors")]
public sealed class DoctorsV1Controller : ControllerBase { }

[ApiController]
[Route("api/v2/doctors")]
public sealed class DoctorsV2Controller : ControllerBase { }

Practice task

Keep an existing v1 client working while introducing an additional field and a new v2 representation.
